# Списки задач по поддереву Redmine: промпты и рецепт

Запросы, которыми из эпика выдёргивают **листовые** задачи поддерева по исполнителю и статусу.
Промпты приведены дословно — их формулировка и есть вход; ниже — что по ним реально исполняется.

## Промпты

```
give me product - based issues leaf nodes from subtree of 11301 that are for user id 127 and 147
sorted by priority decrising. pick out only issues in the backlog state and ожидает дополнения
```

```
give me product - based issues leaf nodes from subtree of 11310 that are for user id 127 and 147
sorted by priority decrising. pick out only issues in the backlog state and ожидает дополнения
```

Третий прогон — тот же текст с корнем 11310: запрос повторяют, когда список нужен на живых данных.
Меняется только номер корня: 11301 (замена UI формы правки графика) и 11310 (этап 3 КП).
Остальное — фильтр: листья, исполнители 127 и 147, статусы «Новая (Бэклог)» и «Ожидает дополнения»,
сортировка по приоритету по убыванию.

```
give me list to delegate to the QA manual, has only browser tools, of leave task in 11310 subtree,
in state "ожидает тестирования", changed from last sunday, assigned user id 128,
order by priority decriasing
```

Четвёртый прогон — тот же обход поддерева, но **один** исполнитель, статус «Ожидает тестирование»
и окно по последнему изменению. Два слова, которые в нём надо перевести в инструмент, — «leave task»
(листья) и «changed from last sunday»: это `updated_on`, а не дата создания. Задача, созданная 21.11 и
принятая в тестирование 22.11, под «created since sunday» не попадает вовсе.

## Что означает каждое слово запроса

| Слово | Как исполняется |
|---|---|
| «subtree of N» | BFS по `GET /issues.json?status_id=*&parent_id=<id>`, без ограничения проектом; `status_id=*` обязателен, иначе закрытые дети в поддерево не попадают |
| «leaf nodes» | задачи, у которых `parent_id` не встречается как родитель ни у одной задачи поддерева — проверять надо по всему поддереву, а не по одному уровню |
| «for user id 127 and 147» | `assigned_to.id` из ответа; имена через `--assignee` по имени не разрешаются (403), поэтому только числовой id. 127 — Трофимов Денис, 147 — Пользователь Технический |
| «backlog state and ожидает дополнения» | `status_id=1` («Новая (Бэклог)») и `status_id=8` («Ожидает дополнения») |
| «changed from last sunday» | `updated_on >= дата`, а не `created_on`: в «ожидает тестирования» задача попадает переводом статуса, и именно он обновляет дату. Дата «прошлое воскресенье» = ближайшее прошедшее воскресенье (`date -d 'last sunday' +%F`), а не воскресенье неделей раньше |
| «priority decreasing» | порядок сервера: 5 Немедленно > 4 Очень высокий > 3 Высокий > 2 Нормальный > 1 Минимальный |
| «product - based» | **в Redmine такого признака нет**: трекера «Продукт» нет (есть Разработка, Ошибка, Поддержка, NFRs/тех. долг), категорий в проекте msb нет, пользовательские поля (`custom_fields`) — только «ДО Автоматизации» и «ПОСЛЕ Автоматизации». Фильтр не применяется; продуктовую часть приходится отсекать вручную — из списка убираются ретро сессий и оснастки (они формально тот же трекер «Разработка») |

## Рецепт

`--parent` в CLI отдаёт только прямых детей, поэтому поддерево обходится скриптом: одна команда
`redmine api` на узел, кэш по родителю, листья — узлы без детей. Скрипт лежит рядом с этим файлом:

```bash
eval "$(grep -E '^export REDMINE_' "$HOME/.profile")"
python3 .pi/skills/redmine-cli/scripts/redmine-subtree-leaves.py 11310 --users 127,147 --statuses 1,8
python3 .pi/skills/redmine-cli/scripts/redmine-subtree-leaves.py 11310 --users 128 --statuses 9 \
    --changed-since 2026-11-22
```

Скрипт печатает в stderr число узлов и листьев поддерева, в stdout — таблицу «# / url / приоритет /
тема», отсортированную по приоритету по убыванию. Пустой результат — это факт, а не сбой: так было на
11301, где все 71 задача поддерева закрыта или отклонена.

`--wide` расширяет таблицу до «# / url / приоритет / статус / updated / исполнитель / трекер / тема».
Узкий набор — то, что читают в заметке; остальное нужно, когда разбирают, почему строка попала в
выборку (статус, дата, исполнитель) — таблица из восьми колонок в чате читается плохо.

В колонке `url` — готовая ссылка `$REDMINE_SERVER/issues/<id>`, а не голый номер: строку вставляют в
заметку или в чат целиком, не собирая адрес руками. `REDMINE_SERVER` берётся из окружения (тот же,
что у `redmine api`), без него — `https://redmine.msb-leasing.ru`; переопределить на один прогон
можно `--server`. Первая колонка — номер пункта, последняя строка stdout — «напечатано: N пунктов»,
чтобы в разговоре сослаться на «пункт 3» и одним числом сказать, сколько всего.

`--changed-since YYYY-MM-DD` оставляет листья с `updated_on >= дата` и дописывает в stderr, сколько
листьев отсекло окно: «пусто из-за окна» (#15912 принят 22.11, но создан 21.11) отличается от «пусто
из-за исполнителя» без второго запроса к Redmine. Колонка `updated` есть в `--wide`, и по ней видно,
сколько листьев стоит вплотную к границе окна. Формат даты только `YYYY-MM-DD`: `--changed-since
22.11.2026` падает с кодом 2, а не читается как пустой список.

## Результаты на момент запроса

- **11301** — поддерево 71 задача, 67 листьев, все `Закрыта` (66) или `Отклонена` (5); задач
  исполнителей 127/147 в статусах бэклога нет вовсе.
- **11310** — поддерево 249 → 252 задачи, 233 → 236 листьев (числа менялись между прогонами); под фильтр
  попало 8 → 10 задач, «Ожидает дополнения» — ноль, все «Нормальный», кроме #15564 «Минимальный».
- **11310, исполнитель 128, «Ожидает тестирование»** (23.11.2026) — поддерево 281 задача, 259 листьев,
  под фильтр попало 15 листьев; с `--changed-since 2026-11-22` остаётся один — #15912. Ещё один
  претендент того же фильтра, #15511, в список не идёт: он родитель, а не лист.

Числа живые: за пятнадцать минут между двумя прогонами #15879 и #15880 ушли в «В работе (спринт)»,
#15881 — в «Ожидает тестирование», #15747 — в «В работе», появились #15886, #15894, #15896, #15898.
Перед действием по списку запрос повторяют.
